# Password Reset Implementation Security Review

Hi! I've reviewed your password reset implementation (`InitChangePassword`, `VerifyOTP`, and `ChangePassword`). You've done a great job establishing a good foundation (hashing the OTP, counting attempts, separating OTP from the final verified token), but there are a few important vulnerabilities and logic flaws that you should resolve before pushing this to production.

Here are the issues I found, why they are problematic, and how you can fix them.

## 1. Brute Force Protection Bypass (Transactional Rollback)
**Severity:** CRITICAL
**Location:** `UserService.java` -> `VerifyOTP()`

**Why it's wrong:** 
You intentionally implemented rate-limiting by counting attempts (`currentAttempts < 4`). However, when verifying a bad OTP, you throw `ResetPasswordException` and bubble it up. 
Because `ResetPasswordException` extends `RuntimeException` (via `CustomBaseException`), and your `VerifyOTP` method is annotated with `@Transactional`, Spring Boot automatically **rolls back the entire database transaction** upon catching the exception. 
Because of this rollback, your `resetCodeEntity.setAttempts(currentAttempts + 1)` and `resetCodeRepository.save(resetCodeEntity)` are completely undone. The attempts NEVER increase, allowing an attacker to infinitely brute-force the 6-digit OTP within the 15-minute window!

**How to fix:**
You can either handle the failure without throwing an exception inside the transaction boundary, or instruct Spring not to roll back for this specific exception by updating your annotation:
```java
@Transactional(noRollbackFor = ResetPasswordException.class)
public Records.ApiResponse<Records.VerifyOTPResponse> VerifyOTP(...)
```

## 2. Authentication Bypass (Empty Verified Token)
**Severity:** CRITICAL
**Location:** `UserService.java` -> `ChangePassword()` & `ResetCodeEntity.java`

**Why it's wrong:**
In `ResetCodeEntity.java`, the default value for `verified_token` is an empty string `""` (and you reset it to `""` after a successful password change). In `ChangePassword()`, you query the database for the user via their `verified_token`.
If an attacker sends a password change request with `{"verified_token": ""}`, the query `findByVerifiedToken("")` is executed. If there happen to be multiple users with an empty string, the query crashes (500 Server Error) due to a `NonUniqueResultException`. However, if there is **only one** user in the database (or only one user whose token is currently `""`), the database successfully returns that user, and the attacker changes their password without ever needing an OTP.

**How to fix:**
In `ChangePassword()`, explicitly validate that `verified_token` is not null and not empty *before* querying the database. Also, it would be much safer to initialize `verified_token` as `null` by default instead of `""`.

## 3. Account Enumeration (User Discovery)
**Severity:** MEDIUM
**Location:** `UserService.java` -> `InitChangePassword()` and `RepositoryRetrieval.java`

**Why it's wrong:**
Your `InitChangePassword` method attempts to be discreet by returning: *"If an account exists, an email to reset your password has been sent."* This is good security practice to prevent attackers from discovering which emails are registered.
However, the first thing the method calls is `repositoryRetrieval.getUserEntityFromEmail(email)`. As implemented, if the email does not exist, this throws an `InvalidUserException` BEFORE the success message is reached. That exception is immediately returned to the client as an error. Therefore, an attacker can just barrage the endpoint with emails and determine precisely which users are registered based on whether they get a 200 OK or an error.

**How to fix:**
Wrap the retrieval in a `try-catch` inside `InitChangePassword` (or use `Optional`). If the user isn't found, do not send the email, but DO instantly return the same generic HTTP 200 OK success message.

## 4. Insecure Randomness for OTP Generation
**Severity:** LOW / MEDIUM
**Location:** `CryptographyUtil.java` -> `generateOTP()`

**Why it's wrong:**
You are using `java.util.Random` for OTP generation. `java.util.Random` is a pseudo-random number generator that is not meant for security purposes. If an attacker requests a few OTPs, they can mathematically deduce the internal state of `Random` and predict all future OTPs generated by your server.

**How to fix:**
Use Java's cryptographically secure random number generator instead:
```java
import java.security.SecureRandom;

public static String generateOTP(){
    SecureRandom rnd = new SecureRandom();
    int number = rnd.nextInt(1000000); // Ensures it handles up to 999999 properly
    return String.format("%06d", number);
}
```

## 5. Missing Token Expiration Check
**Severity:** LOW / MEDIUM
**Location:** `UserService.java` -> `ChangePassword()` and `InitChangePassword()`

**Why it's wrong:**
When `VerifyOTP` succeeds, a `verified_token` is generated. However, when the user finally calls `ChangePassword()`, there is no validation on whether the `expires_at` timeframe has passed. Practically, once a user verifies their OTP, their `verified_token` never expires!
Furthermore, if a user requests a NEW OTP via `InitChangePassword`, you do not wipe out their old `verified_token`. If that token ever leaked, an attacker could change their password at any time in the future.

**How to fix:**
1. In `ChangePassword()`, verify that `TimeUtil.getCurrentTime().isBefore(resetCodeEntity.getExpires_at())`.
2. In `InitChangePassword()`, make sure to explicitly set `resetCodeEntity.setVerified_token(null)` when creating a new OTP so previous tokens are invalidated.
3. Consider assigning a short time extension in `VerifyOTP` (e.g., 5-10 minutes) so the `expires_at` is updated right after OTP verification, giving them just enough time to enter the new password.
